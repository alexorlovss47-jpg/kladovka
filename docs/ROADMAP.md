# Kladovka — Development Roadmap

Основной документ планирования и контроля разработки файлового менеджера Kladovka для macOS.

**Технологии:** Tauri 2, Rust, React 19, TypeScript.

## Правила ведения документа

Статусы задач:

- `[ ]` — не выполнено.
- `[~]` — выполняется.
- `[x]` — выполнено и проверено.
- `[!]` — заблокировано или обнаружена проблема.

### Обязательные правила для AI-агента

1. Самостоятельно анализировать текущую реализацию каждой задачи перед началом работы.
2. Не дублировать уже реализованный функционал.
3. После завершения задачи самостоятельно обновлять её статус в этом файле.
4. Отмечать `[x]` только после успешной проверки реализации.
5. Если задача уже реализована и протестирована, отметить её `[x]`.
6. Если обнаружена проблема, указать её причину и отметить `[!]`.
7. Не переходить к следующему этапу, пока не проверен предыдущий.
8. Не удалять существующие функции и не нарушать обратную совместимость без необходимости.
9. После каждого этапа запускать доступные тесты и проверку сборки.
10. Вести краткий журнал изменений в конце документа.

# Отчёт по Этапу 6

Реализовано 28.11.2026. Диалог «Дополнительно» открывается `⌘E`, четыре
вкладки: архив, переименование, сравнение, размер.

## Архивы

`src-tauri/src/extras.rs` создаёт ZIP через уже имеющийся крейт `zip`
(дополнительных зависимостей не потребовалось). Имена внутри архива —
относительные к общему предку выделенных путей: если выделили содержимое
папки, не создаётся лишняя папка-обёртка.

**Симлинки не включаются** — обход через `file_type()` не разыменовывает,
иначе в архив попало бы содержимое по ссылке.

Распаковка — с защитой от **Zip Slip**: каждый путь проверяется через
`safe_extract_path`, любое `..`, абсолютный путь, обратный слэш или
Windows-диск отклоняются до записи. Ограничение 2 ГБ на запись защищает от
zip-бомб. `sniff_archive` смотрит magic-байты, а не расширение: файл
`fake.pdf` с содержимым ZIP определяется как ZIP.

Поддерживаемые форматы: ZIP — нативно; TAR/GZ/BZ2/XZ распознаются по
расширению и magic; 7z/RAR помечаются как `external` (для них нужен
внешний инструмент, в MVP не распаковываем).

## Пакетное переименование

Шаблон с `{n}` (номер) и `{name}` (старое имя), начальный номер, фильтры по
подстроке имени и расширению. Сначала строится **план** с предпросмотром —
пользователь видит все «было → стало» до применения.

Три правила защиты данных:
- порядок стабилен (пути сортируются), выдача не зависит от порядка выделения;
- конфликт помечается: если два шага дают одно имя, выполняется первый,
  остальные пропускаются;
- `apply_rename_plan` дополнительно проверяет `symlink_metadata(to)` — даже
  если план «чистый», существующий посторонний файл не будет затёрт.

## Сравнение каталогов

По относительным путям и размерам. Четыре категории: только слева, только
справа, различаются (разный размер), одинаковые. **Содержимое не читается** —
для точной сверки байтов есть `find_duplicates` из Этапа 5. Оба дерева
индексируются в `BTreeMap`, результат детерминирован.

## Размер папок

Вычисляется по явному запросу, не при каждом листинге — обход большого
дерева дорог. Симлинки не учитываются, глубина ограничена 128. Есть и
`child_sizes` для будущей колонки «размер папки».

## Копирование пути

`navigator.clipboard.writeText` — путь копируется в буфер обмена. Работает
для выделенного файла и для текущего каталога.

## Сетевые диски

Отдельной реализации не потребовалось: `disk_info` перечисляет все
смонтированные тома в `/Volumes`, включая сетевые, и опрашивает их раз в
3 секунды. Пункт ROADMAP закрыт как покрытый существующей подсистемой.

## Найденное и исправленное

- **Zip Slip с `C:\evil`:** на macOS `Path::is_absolute()` возвращает false
  для Windows-пути (это `Component::Normal`). Добавлена явная проверка
  обратного слэша и буквы диска.
- **Конфликт переименования не определялся:** первая версия сравнивала
  целевой путь только с исходниками, а не с другими целями плана и не с ФС.
  Переписано: конфликтуют последующие шаги с тем же target и посторонние
  существующие файлы.
- **Симметричный конфликт:** когда два файла переименовываются в одно имя,
  конфликтовали оба и ничего не выполнялось. Теперь выполняется первый,
  конфликтует второй.

# Отчёт по Этапу 5

Реализовано 28.11.2026. Два уровня поиска: мгновенный фильтр поверх
загруженного списка и глубокий обход дерева через Rust.

## Быстрый фильтр (`FilterBar`)

Полоса над списком: расширение, минимальный размер, период, тип (всё/файлы/
папки). Работает по уже загруженным записям — без запросов и задержки.
Показывает счётчик «показано N / всего M» и кнопку сброса.

Первое решение, которое пришлось принять: **папки при фильтре по размеру
скрываются**. Размер каталога в `Entry` равен `None`, и показывать его в
выдаче «файлы больше 1 МБ» значило бы нарушить фильтр. Аналогично папки не
проходят фильтр по расширению — у них его просто нет.

## Глубокий поиск (`advanced_search`)

Диалог `⌘⇧F` с тремя вкладками: фильтр, дубликаты, крупные файлы.

Фильтр: имя, расширение, min/max размер, дата «после/до», скрытые, файлы/
папки, глубина, лимит. Результат показывает число просмотренных записей и
признак обрезанной выдачи — пользователь видит, что в дереве есть ещё.

Ключевые правила обхода `src-tauri/src/search.rs`:
- **не следовать по симлинкам**: `file_type()` не разыменовывает, в отличие от
  `metadata()`. Иначе симлинк на родителя даёт бесконечный цикл;
- **глубина считается по детям**: запись внутри каталога на глубине `depth`
  имеет `depth + 1`. Ошибка в первую версию поиска пускала в выдачу файлы из
  каталогов глубже лимита;
- **фильтр по расширению должен реально применяться** — поле было в структуре,
  но проверки в `matches_metadata` не было, и `c.jpg` попадал в поиск `png`;
- лимит останавливает обход, но не делает выдачу «тихой» — выставляется
  `truncated`;
- мусор macOS/Windows (`.DS_Store`, `._*`, `Thumbs.db`) отсекается тем же
  `is_mac_metadata_name`, что и в основном листинге.

## Самые большие файлы

Не сортируем всё дерево: держим буфер размера `limit`, при превышении
выбрасываем минимальный (`smallest_index`). Память O(limit), а не O(файлов).
Глубина ограничена 64, симлинки не обходятся.

## Дубликаты

Стратегия в три ступени, чтобы не читать гигабайты в хэш:
1. Группировка **по размеру** — нет никакого I/O.
2. В группах >1 файла сравнение **первых 64 КиБ**.
3. Кандидаты сверяются по началу и хвосту (по 64 КиБ) — точное сравнение
   байтов, без внешнего крейта хэширования.

Нулевые файлы игнорируются намеренно: они все «одинаковые», и группа из
тысячи пустых файлов не несёт пользы.

# Отчёт по Этапу 4

Реализовано 28.11.2026. Панель быстрого просмотра справа от списка, в стиле
macOS Quick Look.

## Как открывается

- **Пробел** — показать/скрыть (как в Finder).
- **⌘I** — то же через настраиваемые хоткеи.
- **👁** в тулбаре.
- **Esc** закрывает панель, если она открыта, и только потом снимает выделение —
  иначе одно нажатие делало бы два действия.

Панель показывает ровно один выделенный файл: при множественном выделении
она пустая, чтобы не гадать, что показывать.

## Что умеет

- **Изображения** (png, jpg, gif, webp, bmp, tiff, heic, avif, ico) — рендер
  через asset-протокол, плюс разрешение из заголовка файла.
- **PDF** — число страниц и размер. Полный рендер не делаем: для этого нужен
  PDFKit или pdf.js, это отдельная задача.
- **Текст** — первые 512 KiB с подсветкой структуры (monospace, сохранение
  переносов). Если файл больше, показывается плашка с кнопкой «Показать
  начало» — читать гигабайтный лог без спроса нельзя.
- **Двоичные** — определяется по нулевым байтам и доле управляющих символов,
  показывается иконка и размер.
- **Папки** — подсказка открыть, без попытки чтения.
- **Симлинки** — цель ссылки.
- **Метаданные**: тип, расширение, размер, разрешение, страницы, изменён,
  создан, полный путь.

## Разбор заголовков — свой, без зависимостей

`src-tauri/src/preview.rs` — чистые функции без I/O:
- **PNG** — IHDR на смещении 16;
- **GIF87a/89a** — размеры в первых 10 байтах;
- **JPEG** — обход сегментов до SOF0..SOF15, кроме DHT/JPG/DAC (иначе
  наткнёмся на таблицу Хаффмана и получим мусор);
- **BMP** — с модулем высоты, потому что отрицательная высота означает
  перевёрнутое изображение, а пользователю нужен размер;
- **WebP** — три варианта: VP8X (canvas), VP8 (lossy), VP8L (lossless);
- **PDF** — подсчёт `/Type /Page`, при этом `/Type /Pages` (узел дерева)
  явно исключён.

Каждая функция получает срез байтов, поэтому на обрезанном файле возвращает
`None`, а не паникует. Это и проверяют тесты.

## Безопасность больших файлов

Три порога: текст 512 KiB, изображение 64 MiB, PDF 128 MiB. Метаданные
(deшёвый `stat`) приходят всегда, содержимое — только под лимитом. PDF
читается кусками по 8 MiB с начала и конца, а не целиком в память.

Обрезка текста идёт по границе символа UTF-8: иначе на кириллице в конце
показался бы битый символ. Функция `truncate_utf8` отступает назад, пока срез
не станет валидным.

## Asset-протокол

Картинки отдаются через `convertFileSrc`, а не base64 — иначе 20-мегабайтная
фотография раздулась бы в JS-строку. Для этого пришлось:
- включить фичу `protocol-asset` у `tauri` в `Cargo.toml`;
- добавить `app.security.assetProtocol` в `tauri.conf.json`;
- расширить окна в capabilities на `win-*`, иначе во втором окне панель
  не работала бы.

**Грабли:** я сначала добавил permission `core:asset:allow-load` — такой
permission в Tauri 2 не существует, сборка падала с гигантским списком
доступных. Для asset-протокола permission не нужен вообще, достаточно фичи
и конфига.

## Гонка запросов

Быстрое перелистывание файлов стрелками даёт ответы не по порядку: медленный
`preview_info` для большого PDF мог прийти после быстрого для картинки и
перезаписать панель старыми данными. В `usePreview` стоит счётчик `seq` —
устаревший ответ отбрасывается.

# Отчёт по Этапу 3

Реализовано 28.11.2026. Этап целиком про навигацию и интерфейс, поэтому
основная работа — на фронте; в Rust добавлена одна команда.

## Архитектура: панели как дерево состояния

Раньше всё состояние (листинг, история, выделение, сортировка, поиск) лежало
в одном `App.tsx`. Для двух панелей это неприемлемо: общий `Set` выделения
означал бы, что выбор в одной панели гасит выбор в другой.

Введена модель `PanelState { id, tabs: TabState[], activeTabId }`, где
`TabState` содержит **всё** своё состояние: историю с позицией `histIdx`,
листинг, `selection`, `anchor`, `sortKey/sortDir`, `query`, `searchResults`.

Хук `src/hooks/usePanels.ts` (~400 строк) управляет деревом. Ключевое решение:
**все операции принимают `panelId` явно**. Один API обслуживает обе панели и
не зависит от того, какая активна — иначе обработчики из старого рендера
попадали бы в чужую панель.

## Возможности

- **Две панели** (`⌘⇧D`). Вторая создаётся лениво и открывается в домашнем
  каталоге; при выключении уничтожается с сохранением первой.
- **Вкладки** в каждой панели: своя история, свой поиск, своё выделение.
  `⌘T` новая, `⌘W` закрыть, `⌘⌥←/→` переключение. Последнюю вкладку закрыть
  нельзя — иначе панель осталась бы без содержимого.
- **Избранное**: звёздочка на текущий каталог, правый клик по записи в
  сайдбаре убирает её. Хранится в `localStorage`.
- **Три режима вида**: список, сетка (плитки с крупными иконками), компактный
  (без колонки даты). Переключаются в настройках и кнопкой в тулбаре.
- **Контекстные меню**: отдельный компонент `ContextMenu.tsx` с двумя
  наборами — для файла (открыть, Finder, копировать, вырезать, вставить,
  переименовать, корзина, избранное, открыть в другой панели, новое окно) и
  для пустого места (создать, вставить, обновить, скрытые, новое окно).
  Меню не выезжает за границы окна и закрывается по клику вне/Esc.
- **Настройка горячих клавиш**: `KeymapModal.tsx` — 22 действия, каждое можно
  переназначить. При конфликте выдаётся предупреждение, а не молчаливая
  перезапись. Поддерживается сброс одного действия и всех сразу.
- **Справка по клавишам** показывает **текущие** сочетания, а не захардкоженные.
- **Несколько окон**: команда `new_window` создаёт `WebviewWindow` с уникальной
  меткой и опциональным стартовым каталогом.

## Команда new_window

Tauri 2 не позволяет клонировать окно из конфига, поэтому параметры главного
окна продублированы в билдере. Три решения по ходу:

- **Метка из счётчика**, не из `webview_windows().len()`: при закрытии окон
  длина уменьшается и метка повторилась бы → паника на дубликате.
- **Async-команда** — официально требуемый паттерн Tauri: синхронное создание
  окна дедлокнуло бы на Windows (issue с Webview2).
- **Стартовый путь через `serde_json`**, а не ручную подстановку: кавычки,
  обратные слэши и кириллица в имени каталога иначе ломают JS-литерал.
  Вынесено в чистую `start_path_script` — её и проверяют тесты.

## Найденное и исправленное в процессе

- **`focusOtherPane: "Tab"`** — `preventDefault` на Tab ломал переход фокуса по
  кнопкам, а обработчик, пропускавший INPUT/TEXTAREA, не видел фокус внутри
  панели. Заменено на `F6`.
- **Контекстное меню работало с чужой панелью**: `selection`/`entries` брались
  из активной панели, но `setActivePanelId` из клика применяется только в
  следующем рендере. Меню теперь берёт срез панели, на которой открыто.
- **`active`-класс не проставлялся в однопанельном режиме** — панель выглядела
  неактивной.
- **`.main` с `flex-direction: row`** ломал нижнюю строку подсказок и панель
  операций (они позиционируются абсолютно от `.main`). Панели вынесены в
  отдельный `.panes`.
- **Сортировка и выделение дублировались** в `App` и в хуке — при переезде на
  вкладки это дало бы рассинхрон; оставлен единственный источник правды.
- Удалён мёртвый код: `useNavigation.ts` (заменён историей вкладок) и
  `useSortedEntries` (не использовался).

# Отчёт по Этапу 1

Реализовано 28.11.2026. Затронут `src-tauri/src/lib.rs` и `src/App.tsx`.
Публичный API команд расширен только необязательным параметром `conflict`,
поэтому вызовы без него работают как раньше.

## Что изменено

**Симлинки.** Обход переведён на `symlink_metadata` + `file_type().is_dir()`
вместо `path.is_dir()`: ссылка копируется как ссылка (через `fs::read_link` +
`symlink`), а не разыменовывается. Это же свойство закрывает циклы: `a → b → a`
выглядит как обычный линк и не может быть пройден рекурсивно. `count_bytes`
больше не считает объём цели ссылки.

**Копирование в себя.** `ensure_not_inside_source` проверяет все источники до
начала работы и отклоняет операцию целиком, если приёмник совпадает с источником
или лежит внутри него.

**Конфликты имён.** Добавлен `ConflictPolicy` (`rename` по умолчанию, `skip`,
`overwrite`) как необязательный параметр `copy_paths`/`move_paths`. Свободное имя
определяется через `symlink_metadata`, поэтому битый симлинк считается занятым
(раньше `exists()` возвращал false и файл затирался).

**Атомарность.** Файл пишется в `.kladovka-<op>-<n>.part` рядом с целью и
переименовывается только после полной записи. Ошибка или отмена оставляют
исходный файл нетронутым и не оставляют «половину» в приёмнике.

**Откат.** `CopyCtx` ведёт список созданных путей; при любой ошибке или отмене
вызывается `rollback()`, удаляющий их в обратном порядке. Раньше отменялся только
текущий недописанный файл, а уже скопированные оставались.

**Создание файлов.** `create_file` использует `create_new` (не усекает
существующий) и возвращает понятную ошибку. docx/xlsx-скелеты собираются в
временном файле через `create_new_file` и переименовываются атомарно.
`create_dir` больше не `create_dir_all` — не создаёт отсутствующих родителей молча
и не «схлопывается» в существующий каталог.

**Опасные операции.** `delete_paths` (безвозвратное `remove_dir_all` мимо Корзины)
снята с регистрации в Tauri: из UI она недоступна, удаление идёт только через
Корзину. Функция оставлена для внутренних нужд.

**Утечка состояния.** `AppState.cancels` очищается после завершения операции —
карта больше не растёт на каждой операции.

**UI.** При совпадении имён показывается диалог с тремя вариантами вместо
молчаливого переименования. Вариант «Заменить» помечен как опасный.


Тесты покрывают: копирование симлинка как ссылки, цикл без stack overflow,
отклонение копирования в себя (3 варианта вложенности), отсутствие роста дерева,
`create_new` против перезаписи, три политики конфликтов, битый симлинк как
занятое имя, откат при отмене, обратный порядок отката, `count_bytes` без
симлинков, отсутствие `.part` после успеха, rename в пределах ФС, валидность
docx/xlsx, отказ перезаписи Office-файла, нормализацию путей.

## Найденное в процессе

Тесты сразу поймали три дефекта в первой версии правок, все исправлены:

1. `canonicalize().unwrap_or(normalize())` ломал проверку вложенности на macOS:
   `/var` — симлинк на `/private/var`, поэтому существующий источник
   канонизировался, а ещё не созданный приёмник — нет, и сравнение давало ложный
   отрицательный результат. Заменено на канонизацию ближайшего существующего
   предка с приклеиванием остатка.
2. `count_bytes` считала размер цели симлинка вместо нуля.
3. Тест на симлинк проверял недостижимое условие (через ссылку всё равно виден
   оригинальный каталог) — переписан на проверку состава приёмника.

## Осталось за рамками Этапа 1

## 3. Технический долг и риски

### P0 — потеря или повреждение данных

1. **Симлинки разыменовываются при копировании.**
   `copy_with_progress` (lib.rs:307) использует `src.is_dir()`, а `is_dir()` следует
   по ссылке. Симлинк на каталог копируется как полноценный каталог, а не как ссылка.
   `count_bytes` (lib.rs:353) ведёт себя так же — прогресс считает не то.
   *Риск:* неверная семантика копирования, размножение данных.

2. **Нет защиты от циклов — переполнение стека.**
   Обход в `copy_with_progress` и `count_bytes` рекурсивный, посещённые inode не
   отслеживаются. Цикл симлинков (`a → b → a`) даёт бесконечную рекурсию и краш
   приложения. *Риск:* падение, зависание.

3. **Копирование каталога внутрь себя.**
   Проверки «источник не является предком приёмника» нет. `copy_paths("/a", "/a/sub")`
   начнёт писать внутрь источника, `count_bytes` посчитает total заранее и
   разойдётся с реальностью. *Риск:* лавинообразный рост данных, переполнение диска.

4. **`create_file` молча перезаписывает существующие файлы.**
   `fs::File::create` (lib.rs:559), `write_min_docx`/`write_min_xlsx` (lib.rs:568, 600) —
   все используют `File::create`, который усекает файл. UI при этом ждёт ошибку
   «файл с таким именем уже есть» (строка `alreadyExists` в i18n есть, но для
   создания не возвращается никогда — её отдаёт только `rename_path`).
   *Риск:* безвозвратная потеря содержимого при совпадении имени.

### P0 — неполная отмена

5. **Отмена не убирает частичные данные.**
   При отмене `copy_with_progress` удаляет только текущий незавершённый файл
   (lib.rs:319). Уже скопированные файлы и созданные каталоги остаются, откат
   для каталогов отсутствует. Пользователь получает «половину» копии без
   предупреждения. *Риск:* мусор, путаница, ложное впечатление успеха.

### P1 — утечки и производительность

6. **Утечка `AppState.cancels`.**
   `state.cancels.insert(op_id, ...)` при каждом копировании/перемещении
   (lib.rs:369, 424), но запись не удаляется никогда. На длинной сессии — рост
   HashMap. *Риск:* медленная утечка памяти на сотнях операций.

7. **Двойной обход дерева.**
   `count_bytes` полностью обходит источник до начала копирования, затем
   `copy_with_progress` обходит его снова. Для больших каталогов — двойное время
   и двойная нагрузка на диск. При `move` через `rename` дополнительно вызывается
   `count_bytes(&target)` (lib.rs:457) — третий обход.

### P1 — безопасность и корректность

8. **Нет валидации имён.** `create_dir`/`create_file` джойнят пользовательскую
   строку напрямую (`parent.join(name)`), `expand` не канонизирует путь.
   Из UI передать `../` нельзя, но команды доступны через devtools/скрипты.
   *Риск:* выход за пределы ожидаемого каталога.

9. **`delete_paths` не используется во фронте, но зарегистрирована.**
   `fs::remove_dir_all` без подтверждения и без Корзины — мимо защиты
   «восстановимо». Кандидат на удаление или на подтверждение.

10. **CSP отключён** (`tauri.conf.json`: `"csp": null`).

### P2 — тесты и качество

11. **Тестов нет вообще** — ни Rust, ни React. Регрессии ловятся только руками.
12. **`App.tsx` — 1006 строк** в одном компоненте: логика, разметка, модалки,
    горячие клавиши. Дальнейший рост без декомпозиции будет болезненным.
13. **Мусор в рабочем дереве:** `Kladovka_0.1.2_aarch64.dmg` в корне
    (в `.gitignore`, но лежит локально).

## 4. Рекомендуемый порядок работ

1. **Этап 1 (P0)** — начать с пунктов 1–5 отчёта: они либо уничтожают данные,
   либо роняют приложение. Все пять — локальные правки в `lib.rs`, без изменения
   API команд и без риска для обратной совместимости.
2. **Этап 2 (P1)** — очередь операций и очистка `cancels` (пункт 6) логично
   делать вместе.
3. **Этап 8** — параллельно с Этапом 1 добавить первые Rust-тесты именно на
   найденные сценарии (symlink-цикл, копирование в себя, перезапись при создании):
   они станут защитой от повторного появления этих багов.

## 5. Вывод

Проект в рабочем состоянии: сборка, подпись, релиз, внешние диски, локализация,
звуки и горячие клавиши проверены живыми прогонами. Основная проблема —
**незащищённые файловые операции**: четыре сценария ведут к потере или
повреждению данных, один роняет приложение. Это ровно та зона, где по главному
принципу проекта («сохранность данных важнее количества функций») нужно
остановиться и закрыть долг до добавления новых возможностей.
